# 유지보수 가이드

## 데이터 디렉토리 구조

```
data/
├── gensight.db     # 라이브러리·계정·감사 로그·아카이브 (SQLite, WAL 모드)
├── settings.json   # 웹 UI 설정 (디렉토리, 워커, GPU, 언어)
├── gensight-app.log  # 애플리케이션 로그 (로테이션)
├── thumbs/         # 썸네일 캐시 (WebP, 자동 재생성 가능)
├── trash/          # 휴지통으로 옮긴 파일
└── uploads/        # 드래그&드롭으로 업로드된 개별 분석 이미지
```

- **백업**: `gensight.db`와 `settings.json`을 백업하세요. DB에는 재계산이 비싼
  결과(WD Tagger 태그, 품질 점수, 그룹, 평점)가 들어 있습니다. WAL 모드이므로
  서버 중지 후 복사하거나 `sqlite3 data/gensight.db ".backup out.db"`를 쓰세요.
- **캐시 정리**: 디스크 용량이 부족하면 `rm -rf data/thumbs`. 썸네일은 다음 조회
  시 다시 생성됩니다 (`uploads/`·`trash/`는 캐시가 아니라 실제 파일입니다).
- 환경변수 `GENSIGHT_DATA_DIR`로 데이터 디렉토리 위치를 바꿀 수 있습니다.

## 로그

두 가지가 있습니다 — 목적이 다릅니다.

| | 애플리케이션 로그 | 감사 로그 |
|---|---|---|
| 위치 | `data/gensight-app.log` (10MB × 5 로테이션) | SQLite `audit` 테이블 |
| 내용 | 진행률·속도·워커 수·경고 등 동작 추적 | 상태를 바꾼 동작의 영구 기록 |
| 조회 | `tail -f data/gensight-app.log` | 웹 UI **감사 로그** 탭, `/api/audit` |
| 수명 | 로테이션으로 사라짐 | 10만 건까지 보존 후 오래된 것부터 정리 |

`./run.sh start`의 콘솔 출력(`data/gensight.log`)에는 uvicorn 액세스 로그가
함께 들어갑니다. 레벨 조정:

```bash
GENSIGHT_LOG_LEVEL=DEBUG ./run.sh restart
```

기록되는 진행 로그 예:

```
scan 7726072b0902 queued: /imgs (workers=3); 0 running, 1 queued, max 2
scan 7726072b0902: enumerated 12 image file(s) in 0.0s
scan 7726072b0902: 12/12 (100%) 2 img/s, eta 0s
scan 7726072b0902 done: 12/12 processed, 12 with metadata, 6.8s (2 img/s)
tagger using 1 GPU session(s) on device(s) [0], 1 worker(s) each (1 total)
quality analysis started: 500 image(s), 10 worker(s)
watch sweep /imgs: 3 new/changed file(s) ingested (120 known, ...) in 0.4s
```

스캔 중 개별 파일 오류는 서버를 중단시키지 않고 해당 결과의 `error` 필드에
기록됩니다. 썸네일 생성 실패는 `WARNING` 후 플레이스홀더로 응답합니다.

### 감사 로그

계정·설정·스캔·삭제·정리·태깅 등 상태 변경 동작을 누가 언제 했는지 남깁니다
(`actor`는 인증이 켜져 있을 때 세션 사용자, 아니면 `system`). 감사 기록 실패가
원래 동작을 막지는 않습니다. 관리자 전용이며 CSV로 내보낼 수 있습니다.

### 워커 / 동시성 상태

감사 로그 탭 상단에서 실행 중·대기 중 스캔 수, 활성 추출 워커 수, 감시 스레드
상태를 실시간으로 확인할 수 있습니다 (`GET /api/status/workers`).

## 라이브러리 기록 정리 (purge)

### 등록 목록과 카탈로그는 별개입니다

설정의 **스캔 디렉토리**는 즐겨찾기입니다 — 스캔 탭의 자동완성과 이미지 서빙 허용
경로로 쓰일 뿐, 라이브러리 카탈로그와 독립입니다. 그래서 등록을 해제해도 이미
스캔된 기록은 남습니다. 이는 의도된 동작입니다(한 경로를 여러 번 스캔했거나 경로가
겹칠 수 있고, 태그·품질 결과를 잃지 않아야 하므로). 기록까지 지우려면 아래 정리
기능을 쓰세요.

### 사용법

설정 탭 → **기록 정리** 카드, 또는 각 디렉토리 항목의 `기록 정리` 버튼.

| 모드 | 대상 |
|---|---|
| 이 경로의 모든 기록 (`all`) | 해당 경로 하위 모든 행 |
| 파일이 사라진 기록만 (`missing`) | 파일이 실제로 없는 행만 |

**항상 미리보기가 먼저입니다.** 미리보기는 대상 행 수를 파일 존재 여부로 분류하고
(있음 / 없음 / 읽기 실패), 함께 사라질 태그·품질·그룹·평점 건수를 보여주고,
겹치는 등록 경로·활성 감시·실행 중 스캔을 경고합니다. 실행은 미리보기가 발급한
토큰으로만 가능하며, 그 사이 다른 쓰기가 발생하면 **409**로 거부하고 미리보기를
다시 요구합니다.

정리는 **파일을 절대 삭제하지 않습니다** — 라이브러리 기록만 옮깁니다.

### 안전장치

- `mode=missing`인데 **읽기 실패** 행이 하나라도 있으면 중단합니다. 마운트 해제나
  권한 오류를 "파일 없음"으로 오판해 수천 행을 지우는 사고를 막기 위한 것으로,
  마운트를 복구한 뒤 다시 실행하세요.
- `mode=missing`은 **실행 직전에 파일 상태를 다시 확인**합니다. 미리보기 이후
  마운트가 돌아와 파일이 다시 보이면 거부합니다 — 이 변화는 DB에 아무 흔적을
  남기지 않아 버전 검사로는 잡히지 않습니다.
- 대상 경로에 스캔이 실행 중이거나 **감시가 활성이면 거부**합니다. 감시는 타이머로
  다시 수집하므로 정리가 곧 되돌려지고, 진행 중인 sweep과 겹치면 분석 결과가
  아카이브에 갇힌 채 빈 행이 들어올 수 있습니다. 감시를 먼저 끄세요.
- 경로 비교는 `LIKE`가 아닌 리터럴 비교라 `_`·`%`가 들어간 디렉토리명이나
  형제 경로(`img` vs `img2`)를 잘못 포함하지 않습니다.
- 경로 앞뒤 공백을 **잘라내지 않습니다**. `/imgs/set `과 `/imgs/set`은 서로 다른
  디렉토리이므로, 잘라내면 지목하지 않은 옆 디렉토리를 정리하게 됩니다. 공백이
  있으면 미리보기가 경고하고 대상은 0건이 됩니다.
- `.`·`..`가 포함된 경로는 거부합니다. `link/..`를 문자열로 접으면 `link`가
  심볼릭 링크일 때 OS가 가리키는 곳과 달라집니다.
- 미리보기 토큰은 1회용이고, 미리보기 시작 시점의 라이브러리 버전에 묶여
  있습니다. 이 버전은 아카이브 트랜잭션이 쓰기 락을 잡은 뒤 한 번 더 확인됩니다.

## 아카이브

정리된 기록은 삭제되지 않고 `archived_images` 테이블로 스냅샷됩니다. 실수를
되돌릴 수 있고, GPU 재계산을 피하기 위한 것입니다.

- **복구**: 설정 → 아카이브 카드에서 배치 단위로 `복구`. 태그·등급·품질·그룹·
  평점·즐겨찾기가 전부 되살아납니다. 그 사이 같은 경로에 더 새로운 기록이
  생겼다면 새 기록이 이깁니다 — 해당 건수는 `건너뜀`으로 보고됩니다.
- **재스캔 시 자동 부활**: 정리한 경로를 다시 스캔하면 아카이브 행을 복원한 뒤
  메타데이터를 갱신합니다. 태거를 다시 돌릴 필요가 없습니다. 단 같은 경로에
  **다른 파일**이 놓였다면(크기·수정시각 불일치) 복원하지 않고 새로 분석합니다 —
  그러지 않으면 새 이미지가 옛 이미지의 태그를 물려받습니다.
- **보존 기간**: `archive.retention_days` (기본 30일). 경과분은 감시 루프에서
  시간당 1회 자동 정리됩니다. `0`으로 두면 수동으로만 정리합니다.
- **수동 정리**: 아카이브 카드의 `만료분 정리` / `전체 삭제`.
  **전체 삭제는 되돌릴 수 없습니다.**

누락 파일 정리(`POST /api/library/cleanup`)도 이제 하드 삭제 대신 아카이브를
거치고, 읽을 수 없는 파일의 행은 보존합니다.

## 문제 해결

| 증상 | 원인 / 조치 |
|---|---|
| 스캔 시작 시 400 `directory not found` | 경로 오타 또는 서버(컨테이너)에서 보이지 않는 경로. Docker라면 볼륨 마운트 확인 |
| 결과에 `error: PermissionError` | 해당 파일 읽기 권한 없음. 파일은 건너뛰고 스캔은 계속됩니다 |
| 썸네일이 회색으로 표시 | 손상된 이미지 파일 — 원본 확인 |
| 이미지 포함 복사가 텍스트만 복사됨 | 클립보드 이미지 쓰기는 HTTPS 또는 localhost에서만 동작. `127.0.0.1`로 접속하세요 |
| 스캔 작업 목록이 재시작 후 비어 있음 | 작업(job) 진행 상태는 메모리에만 있습니다. 추출된 이미지 기록 자체는 `gensight.db`에 영구 저장되므로 **라이브러리** 탭에 그대로 남습니다 |
| 디렉토리 등록을 해제했는데 라이브러리에 기록이 남음 | 정상 동작입니다 — 등록 목록은 즐겨찾기일 뿐 카탈로그와 독립입니다. 기록까지 지우려면 아래 [라이브러리 기록 정리](#라이브러리-기록-정리-purge)를 쓰세요 |
| 업그레이드 후 새 버튼이 눌러지지 않음 | 브라우저가 옛 `app.js`를 캐시에서 쓰는 상태 — 새 마크업의 버튼에 핸들러가 붙지 않습니다. 강제 새로고침(`Ctrl+Shift+R`)하세요. 정적 파일에 `Cache-Control: no-cache`를 붙여 재발을 막았지만, **그 수정 이전에 캐시된 파일에는 한 번의 강제 새로고침이 필요합니다** |
| GPU가 목록에 없음 | `nvidia-smi` 동작 확인. Docker라면 `nvidia-container-toolkit` 설치 **및 데몬 등록**(`nvidia-ctk runtime configure --runtime=docker` 후 재시작) 필요 |
| `permission denied ... /var/run/docker.sock` | 사용자가 `docker` 그룹에 없음 — [설치 가이드](installation.md)의 "sudo 없이 실행" 참고 (그룹 변경은 재로그인 후 적용) |
| `could not select device driver "nvidia"` | 툴킷이 데몬에 등록되지 않음. `docker info \| grep Runtimes`에 `nvidia`가 보여야 함 |

## 보안 주의사항

- 인증은 **기본적으로 꺼져 있습니다**. 기본값(127.0.0.1) 외 인터페이스로
  바인딩하기 전에 설정 → 인증에서 켜고 관리자 계정을 만드세요. 계정은
  `gensight.db`에 scrypt 해시로 저장되고, 비밀번호·역할이 바뀌면 기존 세션이
  무효화됩니다. 일반 사용자(`role=user`)는 설정·스캔·파일 작업·경로 정보에
  접근할 수 없습니다.
- 파괴적 유지보수 API는 `/api/admin/...` 아래에 있으며 일반 사용자 허용
  목록에 포함되지 않으므로 기본 거부됩니다.
- 이미지 서빙은 등록된 디렉토리 + 스캔한 디렉토리 + 업로드 폴더
  하위 경로로 제한됩니다 (경로 탈출 방지를 위해 `resolve()` 후 검증).
